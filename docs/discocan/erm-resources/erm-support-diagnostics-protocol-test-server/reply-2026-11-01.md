## Fault format (`419`)

R&D decodes `19,0,419,0,1,1,1001,21000010F30701000004DF0B01` as type `21` followed by repeated
records:

- a four-byte SPN;
- a one-byte FMI (0–31);
- a one-byte status, `01` added.

This confirms the four-byte big-endian SPN that discocan decodes. The protocol PDF's one-byte SPN
table is wrong.

## Fault lifecycle

According to R&D:

- eData keeps a buffer of fault codes.
- When it sees a code on the CAN bus that is not in the buffer, it sends an **added** (`01`) event.
- When a code in the buffer has not been transmitted on the CAN bus for more than one minute, it
  sends a **removed** (`02`) event.

A `419` record is therefore a transition of a code that the vehicle currently broadcasts on the
CAN bus. It is not a stored history, and eData learns codes only from the CAN traffic it processes.
CB1147TP shows this behaviour. On 2026-11-07 it added SPN 3719 / FMI 15 at 03:27:52 UTC and removed
it at 03:30:41 UTC. On 2026-11-09 at 14:54:50 UTC, one report removed three codes that had been
added on 2026-11-07.

This resolves the byte 7 discrepancy:

- **Byte 5** is the ignition-off debounce. The Monitor export's debounce `2` belongs here.
- **Byte 7** is ignition-off CAN processing. ERM's SET GLOBAL SETTINGS command writes `02` at byte 7, and
  `01 01 01` at bytes 11–13 (both CAN channels in silent mode, `OBD_Unit` 1). CB1147TP and CB6721TE
  read back `02` at byte 7.

The workbook names the fields but not their value encodings, for example baud-rate code `08` or
the protocol bit masks.
