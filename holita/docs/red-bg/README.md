# Red.bg inventory for the Holita migration

A reference map of the old Red.bg platform, written 2026-11-18, not a plan.

This is an offline, read-only source inventory, not a production census. `E` means `/workspace/projects/red.bg/workspace-ecommerce`; `S` means `/workspace/projects/red.bg/workspace-sales`. Service details and source paths are in [services](services/). Status is what source and current workspace registration describe; running instances, configuration, traffic, data volumes and provider usage were not inspected.

Tracked-file counts come from each service's `git ls-files`; the two infrastructure/data directories marked parent are tracked by their workspace instead. Language line counts in service files exclude restricted paths, image/font files, lockfiles and any storefront `themes` directories; theme and image counts are separate. They include tracked tests, documentation, generated preview HTML and other non-vendor text; bundled code outside identifiable vendor directories may remain; language totals are not application-only estimates. Test counts are test-directory files, including fixtures and helpers, not executed test cases. Route counts are literal source declarations, with each resource macro counted once, not expanded Laravel routes; multi-method declarations can be undercounted. Estimates are relative reimplementation size, not duration.

## Actors and sign-in

- Merchant admin signs in via Auth; Admin initiates PKCE and exchanges a one-time handoff for an API opaque bearer stored in its own server-side session. Store membership is checked by API (`E/docs/auth.md`, `E/services/api/app/Support/Tenancy/StoreContext.php`).
- Platform officer/staff uses Backoffice → Auth → API opaque officer session; Backoffice can initiate authorized Admin impersonation (`E/docs/auth.md`, `E/services/backoffice/app/Http/Controllers/Backoffice/Stores/StoreImpersonationController.php`). A distinct platform-operator identity beyond officer was not found in the skim.
- Shopper uses Basic customer Auth/PKCE and API customer session; Basic also signs service requests with Ed25519. Older `E/docs/auth.md` says this integration is pending, but `E/services/storefront/basic/app/Http/Controllers/CustomerAuthController.php` implements callback/exchange and cart merge.
- Sales agent uses the separate Sales login and Sales user records (`S/services/sales/app/Http/Controllers/Auth/LoginController.php`, `S/services/sales/config/auth.php`). Sales talks to Core using its Ed25519 service identity (`S/services/sales/app/Services/Core/Ed25519ServiceToken.php`).
- MCP clients use API-owned opaque OAuth access issued through Auth; API checks the MCP session. Telephony Sales requests use service bearer plus client ID, while browser credentials are scoped separately (`E/docs/auth.md`, `S/services/telephony/api/README.md`). Crawler's private requests and Sales callbacks have distinct authentication (`S/services/sales/routes/internal.php`, `S/docs/architecture/sales-crawler-data-contract.md`). Exact issuer/capability matrices and all deployed keys were not inspected.

## Migration slices

These are candidate planning slices, not claims that a particular slice can be deployed independently without contract work.

1. **Identity, tenancy and platform foundation:** merchant/officer/customer and separate sales-user identity, store membership, service authentication, authorization, locale and audit. Needs agreement on SaaS tenant boundaries and API-to-subgraph identity/token propagation. Preserve PKCE and impersonation where still needed.
2. **Merchants, stores and operator shells:** Backoffice approval and Admin store lifecycle, plans/entitlements, domains and basic settings. Needs slice 1; store creation currently provisions a set of interdependent defaults in one transaction (`E/services/api/app/Services/Stores/StoreCreationService.php`). Cross-service transactions will need a new explicit consistency design.
3. **Catalog, media and content:** products/variants/inventory, collections, uploads, translations, pages/blog and navigation; depends on store context, authorization and file ownership. Choose migration contracts for IDs and media before copying records.
4. **Shopper storefront and checkout:** routing, render engine choice, carts, pricing/tax, inventory reservation, orders, payments/shipping and notifications; depends on slices 1–3 and provider decisions. Keep checkout, callbacks, refunds and reconciliation together in planning even if delivered incrementally.
5. **Merchant operations:** order/invoice/returns screens, discounts, gift cards, customers/consent, analytics and webhooks. Depends on their corresponding domain APIs and event semantics; preserve historical tax snapshots and idempotency.
6. **Sales CRM and telephony:** sales identities, leads/tasks/contacts, offers and bookings, then call/SMS projections and mobile flows. Depends on identity, Core merchant/store contracts and chosen telephony boundary; can progress alongside catalog once those contracts exist.
7. **Crawler and catalog onboarding:** discovery and site analysis, then source catalog acquisition/review/ingestion. Depends on Sales CRM, Core catalog, service authentication and durable outbox/read contracts. It is a separate subsystem, not merely a Sales UI feature.
8. **Optional integrations and presentation:** marketplaces, ERP/marketing connectors, MCP, advanced themes/editor, website, external channels and reporting after their domain contracts. Confirm actual usage and commercial priorities first.

Retirement candidates are evidence, not instructions to delete: former Platform is documented retired (`E/docs/phase-3-platform-retirement.md`); old storefront is documented retired and held outside this study (`E/docs/roadmap.md`); Telephony V1 storage/runtime is retired (`S/services/telephony/api/README.md`); 43 Admin navigation links are placeholders. Gateway checkout is reference-only in Sales workspace but may represent real hardware elsewhere (`S/services/telephony/gw/README.md`). Basic is an active `main` engine as well as a rollback origin, so do not classify it as rollback-only. Shopify/Native files include thousands of themes and shared historical material; decide engine strategy before estimating a line-for-line rewrite.

2. Should Holita retain the Sales platform, crawler, telephony hardware/mobile capabilities, public website and MCP in its first release, or integrate with them during transition?
3. What are the production data volumes, tenant distribution, retention and cutover/rollback constraints, and must existing IDs and historical records remain stable?
